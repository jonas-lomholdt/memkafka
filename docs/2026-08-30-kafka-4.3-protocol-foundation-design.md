# Kafka 4.3 protocol foundation design

**Date:** 2026-08-30

**Status:** Approved

**Roadmap slice:** Cut 2 in [`kafka-api-parity-roadmap.md`](kafka-api-parity-roadmap.md)

## Summary

MemKafka will vendor a narrowly maintained fork of `kafka-protocol` inside this repository, regenerate its message types from Apache Kafka 4.3.1, and introduce response-aware request routing around the existing capability registry.

This cut makes protocol negotiation, headers, flexible encoding, tagged fields, and unsupported-version behavior exact without widening any advertised MemKafka capability. Generated codec availability is not a behavioral-support claim.

## Goals

- Cover the complete Apache Kafka 4.3.1 request and response schemas in a reproducible local crate.
- Return typed `UNSUPPORTED_VERSION` responses for well-formed, schema-known versions outside MemKafka's advertised window.
- Implement Kafka's special unsupported `ApiVersions` fallback.
- Preserve the correct request and response header versions, including flexible headers and tagged fields.
- Prevent rejected requests from reaching broker behavior or mutating state.
- Keep every existing Java, .NET, Go, Rust, flow-profile, and Kafbat scenario green.
- Keep protocol generation and normal builds free of Kafka-source network fetches.

## Non-goals

- Do not widen any `supported` window in the capability registry.
- Do not advertise a new API key.
- Do not add behavioral support merely because a generated codec exists.
- Do not retain schemas below Kafka 4.3's stable protocol range for legacy clients.
- Do not change broker state machines, configuration, storage, delivery guarantees, or Schema Registry behavior.
- Do not create a separately published protocol crate or another repository.

## 1. Vendored protocol crate

The fork lives at:

```text
crates/kafka-protocol/
├── src/
├── protocol_codegen/
│   └── schema/kafka-4.3.1/
├── Cargo.toml
├── LICENSE-APACHE
├── LICENSE-MIT
└── UPSTREAM.md
```

The starting point is upstream `kafka-protocol-rs` commit:

```text
f0abe7eb99d3d54f48120bf1918623c71ba67cce
```

This includes the decoder allocation-safety fix merged after the `0.18.0` crate release. Generated inputs come from Apache Kafka tag `4.3.1`, commit:

```text
26b251a451ce941d3d7a55e6487bcb7f16b5ad48
```

The package keeps the name `kafka-protocol` and its existing feature names. Its internal version becomes `0.18.0-memkafka.1`, making the fork visible in `Cargo.lock`. MemKafka changes its dependency from crates.io to the local path; imports remain unchanged.

`UPSTREAM.md` records:

- upstream repository and base commit;
- Kafka schema release and commit;
- MemKafka-specific generator changes;
- the procedure for comparing with a future upstream release;
- the condition for returning to crates.io: an upstream release contains the required Kafka schemas and decoder fix and passes this repository's full acceptance suite.

Both upstream licenses and Apache Kafka's notice for the copied schema inputs remain intact.

### Reproducible generation

Only Kafka's official protocol JSON inputs needed by the upstream generator are copied into `protocol_codegen/schema/kafka-4.3.1/`. The generator reads these local files and writes to an explicit output directory. It never clones Kafka.

Two maintainer commands are provided:

```text
scripts/protocol/regenerate.sh
scripts/protocol/regenerate.sh --check
```

Normal regeneration replaces generated Rust deterministically. Check mode generates into a temporary directory and fails on any diff. Normal MemKafka builds never invoke code generation.

## 2. Request pipeline

The connection path becomes:

```text
Kafka frame
  -> fixed request prefix: API key, API version, correlation ID
  -> version-correct request header
  -> Kafka 4.3 body decoder
  -> capability router
       -> supported: Dispatcher
       -> schema-known but unadvertised: typed error response
       -> unrouteable: close only this connection
  -> version-correct response header and body
```

Syntax, policy, behavior, and connection lifetime remain separate:

```text
src/kafka/codec.rs
    Frame, header, and body encoding/decoding only.

src/kafka/request_router.rs
    Chooses dispatch, typed rejection, or connection close.

src/kafka/error_response.rs
    Builds typed error responses for the 17 currently advertised APIs.

src/kafka/dispatcher.rs
    Receives supported requests only and may access BrokerState.

src/kafka/connection.rs
    Owns reads, writes, and the affected connection's lifetime.
```

The capability registry remains the sole source of MemKafka's advertised version windows. The vendored crate supplies syntax and Kafka reference ranges, not support policy.

## 3. Unsupported-version behavior

### Schema-known but unadvertised versions

When the requested version is valid in Kafka 4.3 but outside MemKafka's `supported` window:

1. Decode the header and body using that requested version.
2. Route to `error_response` before `Dispatcher` is called.
3. Build the API-specific response shape with `UNSUPPORTED_VERSION`.
4. Preserve the request correlation ID.
5. Use the response header and body version corresponding to the request version.
6. Copy requested topic, partition, group, or resource identities where the response schema requires them.
7. Set throttle time to zero where present.
8. Write the response and keep the connection usable.

An `acks=0` Produce request still receives no response. Its unsupported version is rejected without append or other mutation.

Error builders have no access to `BrokerState`. This makes state mutation structurally impossible on the rejection path.

### Unsupported ApiVersions fallback

Kafka treats an unsupported `ApiVersions` request specially: it parses the request as an unparsed v0 request and returns an `ApiVersionsResponse` carrying `UNSUPPORTED_VERSION`. MemKafka will mirror Kafka 4.3.1, including its response body/header version and correlation ID. The unsupported body is not decoded optimistically.

References:

- [Kafka 4.3.1 `RequestContext.parseRequest`](https://github.com/apache/kafka/blob/4.3.1/clients/src/main/java/org/apache/kafka/common/requests/RequestContext.java#L112-L129)
- [Kafka 4.3.1 `KafkaApis.handleApiVersionsRequest`](https://github.com/apache/kafka/blob/4.3.1/core/src/main/scala/kafka/server/KafkaApis.scala#L1518-L1535)

### Requests without a response contract

- An unknown API key has no known response schema, so MemKafka logs the key and closes only that connection.
- A non-`ApiVersions` request outside Kafka 4.3's generated schema range cannot be decoded or encoded truthfully, so MemKafka closes only that connection.
- A malformed or truncated header/body closes only that connection.
- An internal response-encoding failure closes only that connection and logs context without exposing record values.

The roadmap wording about response-aware adjacent versions is therefore qualified by schema availability: a typed rejection is required when Kafka 4.3 defines the requested schema. MemKafka does not add legacy codecs solely to answer obsolete versions.

## 4. Typed error responses

`error_response.rs` performs an exhaustive match over the current 17 `RequestKind` variants. Each builder follows Kafka 4.3's request error-response shape:

- top-level error fields where the API defines one;
- per-topic, per-partition, per-group, or per-resource errors where required;
- request identities copied into the corresponding result entries;
- empty payload, assignment, metadata, or records fields where required by the version;
- neutral numeric defaults and throttle time zero;
- no synthetic broker data and no partial success.

Adding an advertised API requires adding its typed rejection builder. A registry/dispatcher/error-builder coverage test fails if these sets diverge.

## 5. Schema and capability invariants

The vendored generated crate is the machine-readable Kafka 4.3 schema source. Tests cross-check every advertised API's capability `kafka43` range against the generated request and response range.

The following concepts remain separate:

- `kafka43`: complete Kafka 4.3 schema range;
- `supported`: MemKafka's currently implemented and advertised range;
- observed client versions: checked-in recorder evidence;
- behavioral proof: named real-client scenarios.

This cut may correct a wrong `kafka43` reference value if generation exposes one, but it may not change `supported` without a separately approved behavioral slice.

## 6. Testing

### Vendored-crate tests

- Generated output is byte-identical in `--check` mode.
- Kafka 4.3 request and response version ranges match the schema inputs.
- The four versions missing from upstream 0.18 are present: ListOffsets v11, OffsetCommit v10, OffsetFetch v10, and InitProducerId v6.
- Classic and flexible headers encode/decode at their version boundaries.
- Unknown tagged fields decode safely and round-trip where applicable.
- The upstream allocation-safety regression test remains present.

### MemKafka protocol tests

For every advertised API:

- the supported floor and ceiling continue to dispatch;
- each adjacent schema-known version outside the supported window returns a correctly shaped `UNSUPPORTED_VERSION` response;
- correlation ID, response-header version, flexible encoding, and tagged fields decode correctly;
- a supported request succeeds on the same connection immediately after a typed rejection;
- the rejection path never invokes the dispatcher.

Focused state tests send rejected Produce, CreateTopics, offset, and group mutations, then prove state is unchanged. Versions outside the generated range and malformed requests prove that only their connection closes.

### Kafka 4.3.1 oracle tests

- A pinned Java helper uses Kafka 4.3.1's request classes to produce normalized expected `UNSUPPORTED_VERSION` response shapes.
- A raw black-box probe compares unsupported `ApiVersions` behavior directly with a digest-pinned Kafka 4.3.1 broker.
- Raw probes are appropriate here because ordinary clients negotiate advertised versions and will not deliberately send unsupported versions.

### Regression suite

The existing unmodified Java, .NET, Go, Rust, Confluent flow-profile, and Kafbat lanes remain unchanged and green. The generated capability manifest and observed request evidence remain byte-identical unless an independently reviewed correction is required.

## 7. CI and packaging

CI adds:

- vendored-crate build and tests with the broker/client/message-enum features used by MemKafka;
- offline regeneration drift checking from the checked-in Kafka 4.3.1 schema inputs;
- capability-to-generated-schema range checks;
- typed rejection and Kafka-oracle black-box tests.

Generated third-party code is formatting-checked and tested but is not churned solely to satisfy MemKafka-specific Clippy style preferences. MemKafka-owned integration code remains under strict Clippy with warnings denied.

The final Docker image still contains only the MemKafka executable. Verification records the release-binary and image-size delta; this design sets no arbitrary size limit, but an unexpected increase must be explained before handoff.

## 8. Acceptance criteria

This cut is complete when:

1. Once ordinary Cargo dependencies are available, MemKafka builds without fetching Kafka source or protocol schemas.
2. Regeneration from the checked-in schema inputs is deterministic.
3. All 17 advertised APIs have exhaustive typed unsupported-version handling.
4. Every schema-known adjacent unsupported version returns a decodable `UNSUPPORTED_VERSION` response and leaves the connection usable.
5. Unsupported `ApiVersions` behavior matches Kafka 4.3.1.
6. Unknown keys, out-of-schema versions, and malformed requests close only their connection.
7. Rejected operations cannot mutate broker state.
8. Capability `kafka43` ranges agree with generated Kafka 4.3 schemas.
9. Advertised `supported` ranges remain unchanged.
10. All existing real-client, Kafbat, evidence, formatting, strict Clippy, test, Docker, and image-cleanliness gates pass.

## 9. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Fork drifts from upstream | Pin provenance, keep upstream structure, minimize patches, and document replacement criteria. |
| Generated code bloats reviews | Separate provenance/schema-generation commits from MemKafka routing commits and review generated diffs mechanically. |
| Codec presence is mistaken for support | Keep `supported` exclusively in the runtime capability registry and leave its ranges unchanged. |
| Rejection accidentally mutates state | Route before dispatch and deny error builders access to `BrokerState`. |
| Flexible header mismatch breaks clients | Test request and response headers independently at every flexible boundary. |
| CI becomes network-dependent or slow | Check in official schema inputs and regenerate offline. |
| Third-party code creates lint noise | Test and format the fork while applying strict MemKafka Clippy rules only to MemKafka-owned code. |

## 10. Follow-on work

After this cut, each API ceiling can be raised only through its own behaviorally complete vertical slice. The next roadmap cut introduces stable topic IDs with `DescribeCluster` and `DescribeTopicPartitions`; it can rely on the protocol and rejection foundation defined here.
